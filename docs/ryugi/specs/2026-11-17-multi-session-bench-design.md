# 多会话并行基准：设计稿

2026-11-17 在架构评审对话里定稿。标「我定的」的是设计者自定、用户未逐条确认的取舍。

## 1. 目的

用户要把「并行多会话」的性能量化出来。现在是零数据：

- `e2e/perf/run.ts` 的 8 项指标全是单会话。
- 界面最多并排 2 个会话，但切走的运行中会话留在后台池继续订阅。真实负载是 2 个前台加 N 个后台。
- 现有回合基准由桥接模拟（`e2e/support/sim-turn.ts` 接管 WebSocket），网关在流式期间不干活。网关一侧从没量过。

这份基准的数字要回答三件事，后面的工作靠它排优先级：

1. 多开会话时，界面还跟不跟手。
2. 多个会话同时流式时，网关的事件循环被占多久。它现在跑在 Electron 主进程里，这个数就是窗口操作会卡多久。
3. 每条消息结束重拉整份历史，一个回合到底多拉了多少字节。

## 2. 范围

| 要做 | 不做 |
|---|---|
| 界面层：分屏与后台池下的输入、帧、流式指标 | 任何优化。只量，不改产品代码 |
| 网关层：N 个真实会话同时流式的事件循环、推送间隔、内存 | 真实模型供应商、远程 workspace |
| 一个真实回合的历史重拉次数与字节（仅 `--web`） | CI 门禁（沿用本地「比上次慢 10% 报错」） |
| 结果并入 `test-results/perf.json` 与现有报告表 | 新的报告页面或文档 |

## 3. 界面层（浏览器，沿用现有 harness）

回合仍由桥接模拟：流速可控，结果稳定。桥接按 `sessionId` 发事件，本来就能同时喂多个会话。

模拟流速（我定的）：每 16ms 一帧 `assistant_delta`，每帧 40 个字，持续 3 秒。16ms 是网关的合帧窗口（`session-runtime.ts` 的 `PROGRESS_COALESCE_MS`），这是界面能收到的最密节奏。

| key | 含义 | 取值 |
|---|---|---|
| `splitTypeWhileStream` | 右侧流式时，左侧输入跟手 | 丢首次，取 7 次中位数（同 `composerKeyToFrame`） |
| `splitDualStreamWorstFrame` | 两侧同时流式的最长帧 | 3 秒内最长一帧 |
| `splitStreamKeepUp` | 两侧同时流式时，左侧增量最慢上屏 | 同 `streamKeepUpMs` 的量法 |
| `bgTypeWhileStream` | 前台输入跟手，同时 4 个后台会话在流式 | 同第一行 |

- 后台会话怎么进池：在会话里开跑回合，再切到别的会话，它就转入后台池（`use-live-subscriptions.ts` 的 `moveToBackground`）。重复 4 次。
- 报告里把这几项和已有的单会话指标排在一起（`composerKeyToFrame`、`streamKeepUpMs`），差值就是并行的代价。

## 4. 网关层（纯 Node，不开浏览器）

在基准进程里起一个真实 `Gateway`，用 WebSocket 客户端同时开 N 个会话并发 prompt。N 取 1、2、4、8。（我定的）

模型用 pi-ai 自带的替身供应商（`@earendil-works/pi-ai` 的 `providers/faux`）：它能按固定速率吐字，也能编排工具调用。每个 prompt 的剧本（我定的）：2 轮工具调用（读工作区里的一个小文件），再吐 400 个 token，速率每秒 100 个。

| key | 含义 |
|---|---|
| `gwLoopP99_<N>` | 流式窗口内事件循环延迟的 p99（`perf_hooks.monitorEventLoopDelay`） |
| `gwFirstProgress_<N>` | 发出 prompt 到收到第一帧 `session_progress`，各会话里的最大值 |
| `gwProgressGapP99_<N>` | 同一会话相邻两帧 `session_progress` 的间隔 p99 |
| `gwRssPerSession` | 8 个会话跑完且仍挂着时的 RSS 减去开跑前，除以 8 |
| `gwTranscriptMs` / `gwTranscriptBytes` | 对长会话种子请求一次全文历史的耗时与字节 |

隔离：照 `run.ts` 现有做法，把 `PI_CODING_AGENT_DIR` 指到临时目录，本机 `~/.pi` 的扩展不进基准。

### 4.1 一个真实回合的历史重拉

这一项要网关和界面都是真的：重拉由界面发起，但次数取决于网关多久广播一次快照。桥接模拟的回合给不出真实次数。

只在 `--web` 模式量（我定的）：这个模式下网关由基准进程启动（`run.ts` 的 `startGateway`），能注入替身供应商。桌面模式的网关在 Electron 里，注入不了，这两项留空。

| key | 含义 |
|---|---|
| `turnRefetchCount` | 在长会话种子里发一个 prompt（剧本同上），整个回合里 `/api/v1/platform/transcript` 的响应数 |
| `turnRefetchBytes` | 同上，响应体总字节 |

**先验证再铺开。** 第一步只做一件事：在网关里用替身供应商跑通一个真实回合（经 `GatewayOptions.createRuntime` 注入）。跑不通就停下报告，不要改网关去迁就基准。

## 5. 输出

- 指标并进 `run.ts` 的 `METRICS`，分两组：「并行（界面）」「并行（网关）」。`config.version` 加一，旧结果不再参与比较。
- 回归规则不变：同口径下比上次慢 10% 以上，退出码为 1。网关层的 p99 若噪声大到规则不可用，执行方报告实测波动，不要自行放宽。（我定的）
- 仍是一条命令：`pnpm test:bench`。网关层先跑，不依赖浏览器。
- 交付时在本机跑一遍，把完整结果表贴在交付说明里。这张表就是用户要的「量化」。

## 6. 约束

- 只动 `e2e/perf/`、`e2e/support/`。产品代码一行不改。
- 守 `AGENTS.md`：单文件不超过 500 行（`measure.ts` 已有 451 行，新场景放新文件）。
- 不引入新依赖。替身供应商来自已装的 pi-ai。
- 基准代码不写单测；它自己就是度量。

## 7. 留给执行方

- 文件怎么分、函数命名。
- 后台 4 个会话的具体编排。
- 网关层的 WebSocket 客户端写法（`packages/gateway/test/` 里有现成样子）。
- 每项跑几轮取中位数，沿用 `--runs`。

## 8. 验收

- `pnpm test:bench --web` 与默认的桌面模式都跑通，新指标全部有数。
- 连跑两次，界面层各项的差在 10% 以内。超出的项要说明原因。
- `pnpm check:touched` 通过。
- 交付说明里有结果表，并对照第 1 节的三个问题各给一句结论。
